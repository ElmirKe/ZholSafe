**Baseline:** `a764843e11c9bbc79d5b83f47feb134b8e218065` (Stage 3; parent `43ee685585f8bd051b69ce6766cfb41dc795ff2e`). Stage 3 tracking is accepted; Stage 4.0 adds image-only analysis. Stage 4.1 distance/TTC methodology, 4.2 Risk Engine fusion and 4.3 DriverGuard remain FUTURE. No Android/device or physical-safety claim follows from desktop unit tests.

## Architecture and input policy

On the existing `zs-processing` thread, `RoadDetectionProcessor` publishes `DetectionSnapshot` → `TrackingSnapshot` → `TrajectorySnapshot`. No queue, long-running thread, model change or additional image buffer. `LinearImageTrajectoryEstimator` implements the upgraded `TrajectoryEstimator.estimate(TrackingSnapshot)` port in pure Java. The old Stage 0 `classify(TrackedObject, w, h)` method remains as a deprecated, conservative `MovementClass.UNKNOWN`: centre points without per-sample source timestamps/boxes cannot honestly classify movement, and mapping pixel growth to `MovementClass.CLOSING` would feed physical risk logic prematurely. Stage 3 `TrackedObject` is **not** mutated. `DistanceEstimator` and `TtcEstimator` remain UNAVAILABLE; no Risk Engine call is added.

A READY tracking snapshot with zero tracks produces a READY trajectory snapshot with zero objects (not a safety judgement). A detector failure, tracker error or model-not-available snapshot yields `TrajectorySnapshot.TRACKING_UNAVAILABLE` with its upstream status and **no objects**. A thrown/mismatched estimator result yields `ESTIMATOR_ERROR` without overwriting successful detection/tracking results. The initial state is `NOT_STARTED`. The engineering report labels values "image/normalized only"; the Stage 3 track-ID box overlay continues unchanged and never draws LOST boxes.

Each track gets an immutable `ObjectTrajectory` with track ID, canonical class, last matched box/centre, source timestamp, number of observations examined and explicit status/quality. Only currently observed CONFIRMED tracks with `missedFrames==0` and last observation at the snapshot timestamp can yield `AVAILABLE`; tentative/LOST/stale tracks yield `TRACK_NOT_CURRENT` and **NaN unavailable** image-motion/scale fields. Retaining a non-current entry (not numeric motion) makes coasting visible to diagnostics. Unavailable entries never output a fabricated zero. Available fit residuals and time span are diagnostics, not calibrated confidence.

## Coordinates, time and fit

Upright source image origin top-left: **+X right, +Y down**; direction is NOT a geographic heading. Current centre is in upright pixels; for a frame of W×H pixels, sample centres are `x_n = (x1+x2)/(2W)`, `y_n = (y1+y2)/(2H)`. `normalizedArea = ((x2-x1)/W) * ((y2-y1)/H)` is a dimensionless fraction (0,1]. Width/height trends are represented via this area rather than claimed physical size.

Use only Stage 3 `TrackObservation.timestampNanos` (positive, same-source nanoseconds). For each sample, `t_i = (timestamp_i - firstTimestamp) / 1e9` **seconds**; the subtraction happens in integer nanoseconds before conversion to double (large clock origins remain precise). Neither `System.nanoTime()` nor processing FPS is used as a motion input; the existing processing clock still measures detector telemetry separately. Timestamps must increase strictly, and the last observation must correspond to the current track. Bad ordering or duplicates → `INVALID_TIMESTAMPS`, not an arbitrary frame interval. A short positive span below the configured minimum → `LOW_QUALITY`. A single/too-few samples → `INSUFFICIENT_HISTORY`.

Take only the most recent `min(history.size, maxSamples)` observations; the Stage 3 history is itself bounded, and the estimator is stateless. Fit normalized centre X, Y and `log(normalizedArea)` separately using ordinary least squares against **actual** source time. For z in {x_n, y_n, log(A_n)}, `slope = Σ((t_i-t̄)(z_i-z̄)) / Σ((t_i-t̄)^2)`. The denominator must be positive/finite. Centre RMS is `hypot(RMS_x,RMS_y)` in normalized-frame fractions; log-area RMS is dimensionless. Excess residuals, nonfinite/degenerate/out-of-frame boxes or nonfinite fits → `LOW_QUALITY` with unavailable numeric values. This is multi-sample smoothing, not a claim that regression is robust to all outliers.

`ImageMotion.velocityXFrameWidthsPerSecond` has units **frame-width fractions/second**; `velocityYFrameHeightsPerSecond` has units **frame-height fractions/second**. `normalizedSpeedPerSecond = hypot(vx,vy)` is a magnitude in normalized-frame fractions/second; because the axes use their respective dimensions it is NOT a metric speed. Direction becomes STATIONARY at/below the normalized speed threshold; otherwise a minor component less than `diagonalComponentRatio × major` gives LEFT/RIGHT/UP/DOWN, else a diagonal combination. Available stationary motion legitimately has velocity zero; unknown motion instead has `available=false`, NaN and `UNCERTAIN`.

`ImageScaleTrend.logAreaRatePerSecond` is `d(log(A_n))/dt` in **dimensionless per second**; positive = apparent image growth, negative = shrink. Absolute rate at/below the stable band → STABLE/LATERAL_OR_STABLE. A slope at/above positive growth threshold becomes GROWING/APPROACHING **only when every consecutive log-area step rate is greater than the configured stable band**; an equally strong negative slope becomes SHRINKING/RECEDING only when every step is below the negative stable band. A one-off box jump or intermediate slope → UNCERTAIN. This is intentionally conservative, though sensitive to one noisy reversed step. These approach/recede labels are **qualitative bounding-box evidence ONLY**: zoom, camera ego-motion, pose, occlusion and changing box quality also change apparent area. Do not infer metres, m/s, collision likelihood or TTC from them.

## Configuration / quality gates

`TrajectoryConfig.defaults()` (experimental engineering, **NOT validated safety thresholds**): `minSamples=3`, `maxSamples=8` (Stage 3 default history 30), `minimumTimeSpanSeconds=0.25`, `stationaryVelocityThreshold=0.012 normalized fractions/second`, `diagonalComponentRatio=0.35`, `scaleStableThreshold=0.03 /s`, `approachGrowthThreshold=0.12 /s`, `recedeShrinkThreshold=0.12 /s`, `maxCenterRmsFraction=0.03`, `maxLogAreaRms=0.12`. All values validated (finite, correct signs/order, min samples ≥3, max≥min). `FIT_ACCEPTED` means only that these residual and span gates passed; it is NOT accuracy or calibrated confidence. If history contains fewer than configured minSamples, no values are invented even if maxSamples is larger than the tracker history.

`ImageMotion` and `ImageScaleTrend` enforce NaN/UNCERTAIN for unavailable values; `ObjectTrajectory` enforces this whenever status != AVAILABLE, and `TrajectorySnapshot` copies its list and distinguishes READY from upstream unavailability. Frame dimensions must be positive for READY; source boxes must be finite, nondegenerate and within the same upright frame size. The latter assumes consistent analysis resolution across one track: Stage 3 history does not store per-observation W/H, so a camera resolution change mid-track must start a fresh tracker/pipeline before interpreting normalized history.

## Tests and limitations

Re-run core tests via `cd android-app && gradle :core:test` when the official Gradle/JUnit toolchain is present; a local fallback for core is `scripts/jvm-fallback-build.sh` with JDK/ECJ/JUnit jars configured. New synthetic JVM tests exercise stationary, cardinal/diagonal directions, scale growth/shrink/intermediate, alternating jitter and fit rejection, history/quality/timestamps, irregular intervals, large timestamp origins, two resolutions, stale tracks, upstream and estimator failures, bounded recent window, immutable contracts and no physical estimates. The Stage 2.5 31-image real-model run is NOT repeated: inference/preprocess/decoders are unchanged. Report exact executions separately; **ANDROID BUILD: NOT EXECUTED** unless an APK was actually built.

Known limitations: no motion prediction, ego-motion compensation, camera calibration, per-sample frame dimensions, robust outlier-resistant fitting or validated safety thresholds; correlation from a few boxes can be misleading; overlapping/occluded tracks can change ID; normalized centre speed mixes width/height axes; apparent growth is NOT physical approach. These labels MUST NOT drive a collision warning or be converted to distance, physical speed or TTC without future separately validated methodology.
