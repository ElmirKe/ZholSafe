# Stage 3 — RoadGuard multi-object tracking

Baseline `43ee685585f8bd051b69ce6766cfb41dc795ff2e` (Stage 2.5). Stage 3 now means **tracking**; DriverGuard is deferred (now scheduled for Stage 4.3; see roadmap). This is a **ByteTrack-inspired** MVP, **not** an exact implementation of the published ByteTrack algorithm. No physical measurements, trajectory model or risk scoring are implemented here.

## Path and contracts

`FramePipeline` retains one processing executor and single-slot `LatestFrameQueue`. `RoadDetectionProcessor` runs the existing `RoadDetector` (unchanged) and, on success only, calls `ByteTrackInspiredTracker.update(detections, frame.timestampNanos())` inline. It publishes the existing `DetectionSnapshot` and a separate immutable latest `TrackingSnapshot`. The `ObjectTracker` signature and `TrackedObject` record constructor remain compatible. `TrackView` wraps a `TrackedObject` with `TrackState`, hit/miss counts, and immutable `TrackObservation` history. `TrackingSnapshot.confirmedObjects()` includes **currently observed confirmed** objects only; LOST boxes are stale, and tentative tracks are not reliable risk input. Future Stage 4.0 image-space estimators consume confirmed tracks **downstream**; Stage 3 never runs them.

`TrackingSnapshot.status`: `NOT_STARTED`, `READY` (includes successful empty detections), `DETECTOR_UNAVAILABLE`, `TRACKER_ERROR`. Unavailable snapshots contain **no tracks**, not a claim that the road is clear. `frameTimestampNanos` for a failure comes from the failed frame if one exists. The detection snapshot remains available if the detector succeeded but tracking rejected its timestamp/input.

## Association and lifecycle

* Canonical `ObjectClass` equality is required; model-specific numeric `classId` is never used. UNKNOWN associates **only** with UNKNOWN, never bridging a known class. A high-scoring UNKNOWN may start a tentative track, but is not re-labelled.
* Pass 1: greedy IoU matching between all existing tracks and detections with confidence `>= highConfidenceThreshold`. Pass 2: remaining **confirmed/lost** tracks against low detections with confidence `>= lowConfidenceThreshold` and `< highConfidenceThreshold`. Scores below the low threshold are ignored. No low-score detection starts or confirms a tentative track.
* Candidate pairs require IoU `>= iouMatchThreshold`. Sort by decreasing IoU, then increasing track ID, then increasing input detection index. Each track and detection can be matched once per pass; pass 1 matches are excluded from pass 2. This is deterministic greedy assignment, **not** Hungarian, Kalman prediction or official ByteTrack.
* A high detection unmatched after both passes starts a TENTATIVE track (or CONFIRMED immediately if `minHitsToConfirm=1`), subject to capacity. `minHitsToConfirm` **consecutive high hits** confirms it. A tentative miss (including unmatched low detections) removes it. A confirmed track with one successful empty/unmatched frame becomes LOST and can recover by either pass before expiry, preserving its ID. After `maxCoastFrames` missed *successful detector frames*, it is removed on the next miss. REMOVED is never output. IDs start at 1, increase monotonically and are **not reused**, including after `reset()`; reset clears tracks and the source timestamp domain. New processor instances have new ID namespaces.
* Age counts successful detector frames since creation, including misses; hit count counts associated observations. LOST `TrackedObject.box` and `timestampNanos` retain the **last observed** box/source timestamp, not an extrapolation. Its `missedFrames` signals staleness. Output is sorted by increasing track ID. The Android overlay skips LOST and labels other tracks with ID and `(tentative)` when appropriate.

## Defaults, memory and clock policy

`TrackingConfig.defaults()`: IoU **0.30**, high **0.50**, low **0.35**, consecutive hits **2**, max coast **10 successful frames**, history **30 observations**, max active tracks **128**. These are engineering defaults, **not calibrated accuracy/performance results**. Constructor validates finite thresholds `[0,1]`, `0 < IoU <= 1`, `0 <= low < high <= 1`, positive frame/history/cap values. Existing corridor fractions are reserved for future stages and are not used here.

Track state is bounded by `maxActiveTracks`; each track stores at most `historyLength` timestamp/box/confidence observations (centres are derived for `TrackedObject.positionHistory`). No pixels, `Frame`, tensor or camera buffer is retained. To bound matching memory even on excessive input, select at most `maxActiveTracks` detections per frame by **descending confidence**, then **earlier input index**; remaining candidates are deliberately ignored (the detector normally caps output itself). If full, unmatched new high detections are not enrolled; old lost tracks retain capacity until expiry. Greedy matching is quadratic in the capped pair count; no profiling/Android performance claim is made.

Tracking requires a **positive, strictly increasing same-source frame timestamp** and each detection timestamp must equal it. Null/nonfinite/degenerate boxes and mismatched timestamps fail explicitly **before tracker state mutation**; an out-of-order frame becomes `TRACKER_ERROR` in the pipeline and throws, rather than fabricating motion or counting a miss. After an error, later valid frames can recover. `reset()` is required on source change or replay restart; the app creates a fresh tracker on every source/mode start. `System.nanoTime()` is used only for processing-time telemetry (existing detector code), **never** for tracking/history motion timestamps.

Detector failure/unavailability **freezes** tracks and the last successful source timestamp; it publishes `DETECTOR_UNAVAILABLE` and rethrows for existing pipeline degradation telemetry. No miss counter is incremented. On the next successful frame the tracker resumes; frozen LOST tracks can still be associated. This is a frame-count policy, **not** a time-based guarantee: after a long outage an old box may still be matched; future safety stages must not treat LOST as an observation. Successful zero detections, conversely, run the normal miss/expiry lifecycle.

`TrackedObject.estimatedDistance` and `.estimatedTtc` are always `Estimate.unavailable()` (`NOT_AVAILABLE`), `movement=UNKNOWN`, `inDrivingCorridor=false`. No metric distance, physical speed, TTC or collision risk is inferred from pixel motion.

## Verification and known limitations

JVM tracking tests use synthetic canonical `Detection` streams, not a model; regression of Stage 0–2.1 core detector/decoder/pipeline tests should use `cd android-app && gradle :core:test` when Gradle and JUnit are available. The Stage 2.5 real-model smoke report stands unchanged: the large 31-image ONNX run is not repeated because detector/decoder inference was not changed. Android APK/device tracking inference is **NOT VERIFIED** unless separately built and run with an Android SDK and genuine model assets; the overlay source change is not a device result. Test execution details for this session belong in the final report.

Limitations: greedy IoU may swap IDs on crossings, occlusion, small fast motion or similar overlapping objects; no appearance embeddings or motion prediction; detector-class flips create new tracks; no class aliases except canonical label map upstream; capacity can omit crowded detections; LOST recovery after prolonged detector failure has no wall-time expiry; tracked IDs are local to one tracker instance and are not persistent across app restarts. No mAP, MOT accuracy, FPS, Android latency, physical quantity or safety efficacy has been measured in this stage.
